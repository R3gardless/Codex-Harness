# 최상위 모델 없이 진행하는 개발 전략

최상위 모델 접근을 전제로 하지 않습니다. 이미 제공되고 허용된 모델을 쓰며 실제
선택지는 `/model`에서 확인합니다. 아래 이름은 화면에 해당 선택지가 있을 때의 예시이고
API 모델 ID나 모든 계정의 사용 가능 목록을 뜻하지 않습니다. 설정에 모델을 고정하지 않습니다.

## 내가 운영한다면

| 작업 | 선택 기준 | 예시 |
| --- | --- | --- |
| 요구사항 해석, API/보안 경계, 어려운 원인 분석 | 허용 모델 중 추론이 안정적인 하나를 주력으로 유지 | Sol 6.1, 없으면 Sol 6.0 |
| 명확한 범위의 구현·수정·테스트 | 주력 모델 그대로 사용; 전환 비용이 이득보다 작을 때만 경량화 | Terra 5.6 |
| 파일 위치 찾기, 형식 정리, 작은 반복 수정 | 맥락이 짧고 결과를 쉽게 검증할 수 있을 때 | Luna 6 |

작업마다 모델을 바꾸지는 않습니다. 코드·결정 맥락을 다시 전달하는 비용이 크면
주력 모델로 계속 진행합니다. 난해한 문제만 더 깊게 생각하게 하고, 쉬운 작업에서는
범위를 줄여 빠르게 검증합니다. 허용되지 않은 상위 모델이나 별도 제공자로 우회하지 않습니다.

## 한 번의 요청에 주는 계약

```text
목표: 사용자가 관찰할 수 있는 결과
근거: 관련 파일 또는 확인된 요구사항
범위: 이번에 바꿀 기능과 유지할 인터페이스
입출력: 스키마와 중요한 오류 조건
통과 기준: 실행할 테스트와 기대 동작
전달: 바꾼 이유, 실제 검증 결과, 남은 한계
```

처음부터 전체 앱을 맡기지 않습니다. 모호한 요구를 정리한 다음 핵심 데이터 흐름
하나를 연결합니다. UI 작업은 코딩 전에 톤앤매너·화면 동선·주요 상태를 설계하고,
API 계약과 테스트를 맞추면서 다크모드·반응형을 포함한 흐름을 완성합니다.

FE와 BE는 같은 API 스키마를 보게 하고 mock과 실제 응답이 다르지 않게 합니다.
각 단계의 완료 조건은 코드 양이 아니라 동작하는 흐름과 검증 근거입니다. 보안·오류
처리는 마지막 장식 단계로 미루지 않습니다.

## 단계별 완료 기준

| 단계 | 집중할 일 | 다음 단계로 넘어갈 기준 |
| --- | --- | --- |
| 맥락 확인 | README·환경·데이터·업무 질문 | 목표·필수조건·불확실성 구분 |
| 설계 | 기능 규칙·정상/예외 흐름·상태/복구, API 계약, UI 방향 | 작은 구현 범위와 검증 기준 확정 |
| 구현 | 종단 기능, 의미 있는 테스트 | 실제 입력으로 핵심 흐름 동작 |
| 검증 | 권한·오류·경계값·통합·UX | 중요 실패 수정 및 근거 확보 |
| 전달 | 실행법·설계 이유·한계·변경 리뷰 | 설명 가능한 결과와 정확한 상태 |

마감이 있으면 실행·응답 대기를 고려해 위임하고, 검증·문서 작성·제출 시간을 먼저
확보합니다. 일정이 밀리면 부가 범위를 줄이고 확인할 시간이 없는 위임을 시작하지
않습니다. 시간 안배도 AI 활용 역량이며, 예산·반환 시점·지연 대응의 상세 기준은
[토큰·에이전트 운영](TOKEN_AND_AGENTS.md)을 따릅니다.

## 막혔을 때의 기준

- 같은 오류를 반복하면 모델 교체 전에 최소 재현·실패 로그·가설을 정리합니다.
- 한 번의 수정이 너무 크면 데이터 모델, 도메인 함수, API, UI처럼 검증 가능한
  경계로 나눕니다. 경계는 실제 프로젝트 구조에 맞춥니다.
- 요구가 바뀌면 이유를 결정 기록에 남기고 통과 기준부터 갱신합니다.
- 주력 모델이 내놓은 설명도 코드·테스트로 대조합니다. 테스트 통과가 전체 보안을
  증명하지 않고, 문서 작성이 사람이 이해했다는 증거도 아닙니다.
- 최종 설명 전에 “한 요청이 어디를 지나가나, 왜 이 구조인가, 어디서 실패하나,
  어떤 테스트가 이를 확인하나”를 본인이 설명할 수 있는지 점검합니다.

상위 모델의 부재를 긴 프롬프트나 많은 도구로 메우기보다, 범위를 명확히 하고 짧은
구현·검증 반복으로 보완하는 전략입니다. 실제 성과는 사용하면서 확인합니다.
